# 코스 상점 방문 체크와 방문 로그 중복 정책 설계

## 목적

사용자가 코스를 따라 이동하면서 각 상점의 방문 여부를 간단히 체크하고, 원할 때만 공개 방문 로그를 이어서 작성하게 한다. 방문 체크는 코스 진행 상태이고 방문 로그는 공개 기록이므로 서로 독립적으로 저장한다.

동시에 실수나 연속 제출로 같은 상점·같은 방문일의 공개 로그가 반복 생성되지 않게 한다.

## 확정 정책

### 방문 로그

- 같은 사용자는 같은 상점에 여러 날짜의 방문 로그를 남길 수 있다.
- 동일 사용자·상점·한국 날짜의 활성 방문 로그는 1개만 허용한다.
- 삭제된 로그는 중복 판단에서 제외하므로 같은 날짜로 다시 작성할 수 있다.
- 중복 여부는 보상 계산만이 아니라 생성 시점에 차단한다.
- 프론트엔드 확인은 안내용이며 최종 보장은 데이터베이스 고유 인덱스가 담당한다.
- 중복 요청에는 `409 VISIT_LOG_ALREADY_EXISTS`를 반환한다.

### 코스 상점 방문 체크

- 방문 여부는 사용자별·코스별·상점별 상태다.
- 같은 상점이 여러 코스에 있어도 각 코스의 체크 상태는 독립적이다.
- 방문 체크와 방문 로그는 서로 자동 생성·수정·삭제하지 않는다.
- 로그 작성 도중 이탈하거나 작성에 실패해도 앞서 저장된 방문 체크는 유지한다.
- 방문 체크를 해제해도 기존 방문 로그는 유지한다.
- 체크 저장과 해제는 같은 요청을 반복해도 결과가 같은 멱등 동작으로 처리한다.

## 사용자 흐름

### 미방문 상태

1. 코스 상세 상점 행의 `방문했어요` 버튼을 누른다.
2. `방문 로그를 작성하시겠어요?` BottomSheet를 연다.
3. `방문만 기록`을 누르면 방문 상태를 저장하고 BottomSheet를 닫는다.
4. `로그 작성하기`를 누르면 방문 상태를 먼저 저장한 뒤 해당 상점이 선택된 방문 로그 작성 페이지로 이동한다.
5. 방문 상태 저장이 실패하면 이동하지 않고 기존 미방문 상태와 오류 안내를 유지한다.

### 방문 완료 상태

1. 활성화된 `방문 완료` 버튼을 다시 누른다.
2. 확인창 없이 방문 상태를 해제한다.
3. 해제가 실패하면 활성 상태를 유지하고 오류를 안내한다.
4. 해제 뒤 다시 누르면 미방문 상태의 처음 흐름을 반복한다.

### 방문 로그 중복

- 작성 화면의 기본 방문일은 오늘이다.
- 같은 상점·날짜의 활성 로그가 이미 있으면 제출 시 중복 오류를 화면에 표시한다.
- 수정 화면이 구현되기 전에는 `같은 날짜의 방문 로그가 이미 있어요. 다른 날짜를 선택해 주세요.`라고 안내한다.
- 수정 기능이 추가되면 중복 오류에서 기존 로그 수정 화면으로 이동하는 동작을 후속으로 연결한다.

## 화면 설계

### 코스 상세 상점 행

- 기존 상점 정보와 길찾기 액션을 유지한다.
- 각 상점 행에 독립적인 작은 방문 버튼을 둔다.
- 미방문은 outline 스타일의 `방문했어요`, 방문 완료는 체크 아이콘과 활성 색상의 `방문 완료`로 표시한다.
- 색상만으로 상태를 구분하지 않고 문구와 `aria-pressed`를 함께 바꾼다.
- 저장 중에는 해당 상점 버튼만 비활성화하고 중복 요청을 막는다.
- 상점 행의 다른 액션을 눌렀을 때 방문 버튼 클릭이 함께 실행되지 않게 이벤트 영역을 분리한다.

### 방문 로그 제안 BottomSheet

- 제목: `방문 로그를 작성하시겠어요?`
- 설명: `방문만 기록하거나, 사진과 태그를 남길 수 있어요.`
- 보조 버튼: `방문만 기록`
- 주요 버튼: `로그 작성하기`
- 바깥 영역이나 뒤로가기로 닫으면 방문 상태를 저장하지 않는다.

### 상점 상세

- 기존 `방문 로그 작성` CTA의 문구를 `방문했어요`로 바꾼다.
- 상점 상세에는 코스 진행 상태가 없으므로 코스용 방문 체크를 만들지 않고 방문 로그 작성 화면으로 바로 이동한다.
- 같은 역할의 CTA를 중복 배치하지 않는다.

## 데이터 모델

### VisitLog 방문일 키

`visitedAt`만 고유 인덱스에 사용하면 같은 한국 날짜를 서로 다른 시각으로 보낸 요청을 막을 수 없다. 서버가 `visitedAt`에서 한국 날짜를 계산해 `visitedDate`를 함께 저장한다.

```text
VisitLog
├─ visitedAt: Date
├─ visitedDate: YYYY-MM-DD
└─ status: active | deleted
```

- 부분 고유 인덱스: `{ userId: 1, shopId: 1, visitedDate: 1 }`
- 조건: `{ status: "active" }`
- 기존 조회용 인덱스는 유지한다.
- 서비스는 저장 전 중복을 확인해 이해하기 쉬운 오류를 반환한다.
- 동시 요청 경쟁은 고유 인덱스 충돌을 같은 `VISIT_LOG_ALREADY_EXISTS` 오류로 변환해 막는다.

기존 데이터에는 `visitedDate`가 없으므로 인덱스 생성 전에 한국 날짜로 역산해 채운다. 같은 키의 활성 로그가 여러 개 발견되면 자동 삭제하지 않고 로그 ID를 보고한 뒤 인덱스 생성을 중단한다.

### CourseShopVisit

```text
CourseShopVisit
├─ userId: ObjectId
├─ courseId: ObjectId
├─ shopId: ObjectId
├─ createdAt
└─ updatedAt
```

- `{ userId: 1, courseId: 1, shopId: 1 }` 고유 인덱스
- 문서가 있으면 방문 완료, 없으면 미방문으로 해석한다.
- 별도의 `isVisited` boolean은 저장하지 않는다.
- 코스 삭제 시 연결된 방문 체크를 함께 삭제한다.
- 상점이 해당 코스에 포함되어 있는지 서버에서 확인한다.
- 사용자가 조회할 수 있는 코스에서만 방문 상태를 변경할 수 있다.

## API 계약

### 방문 로그 생성

- `POST /shops/:shopId/visit-logs`
- 중복: HTTP 409, `VISIT_LOG_ALREADY_EXISTS`

### 코스 상점 방문 상태

- `PUT /courses/:courseId/shops/:shopId/visit`: 방문 완료 상태 보장
- `DELETE /courses/:courseId/shops/:shopId/visit`: 미방문 상태 보장

두 API는 로그인 사용자만 호출할 수 있다. 이미 원하는 상태여도 성공하며 현재 `isVisited`를 반환한다.

코스 상세 응답의 각 상점에는 로그인 사용자 기준 `isVisited: boolean`을 포함한다. 비로그인 사용자는 모두 `false`로 표시하고 버튼을 누를 때 로그인 안내를 시작한다.

## 상태와 캐시

- 방문 토글 성공 시 해당 코스 상세 캐시의 상점 `isVisited`를 갱신한다.
- 낙관적 갱신을 사용한다면 실패 시 이전 상태로 되돌린다.
- `로그 작성하기`는 방문 저장 성공 뒤에만 페이지를 이동한다.
- 코스 진입 정보는 신뢰할 수 있는 내부 경로만 허용하고, 작성 완료 후 해당 코스 상세로 복귀한다.
- 작성 화면을 직접 열거나 상점 상세에서 들어온 기존 복귀 동작은 유지한다.

## 오류 처리

- `401 UNAUTHORIZED`: 로그인 안내
- `404 COURSE_NOT_FOUND`: 코스를 찾을 수 없음
- `404 SHOP_NOT_IN_COURSE`: 코스에 없는 상점
- `409 VISIT_LOG_ALREADY_EXISTS`: 같은 날짜의 활성 로그 존재
- 방문 상태 요청 실패: 버튼 상태 복원과 스낵바 안내
- 방문 로그 중복: 입력값을 유지하고 방문일 근처에 오류 표시

## 기존 데이터 적용

1. `visitedDate` 백필 스크립트를 dry-run으로 실행한다.
2. 활성 중복 키와 관련 로그 ID를 출력한다.
3. 중복이 없을 때만 백필과 부분 고유 인덱스를 적용한다.
4. 중복이 있으면 자동 삭제·병합하지 않고 정리 방법을 별도로 결정한다.

## 테스트 전략

### 백엔드

- 한국 날짜 경계에서 `visitedDate`가 올바르게 계산되는지 검사한다.
- 동일 사용자·상점·날짜 중복과 동시 요청 충돌이 409로 변환되는지 검사한다.
- 다른 사용자, 상점 또는 날짜는 허용되는지 검사한다.
- 삭제된 로그와 같은 날짜는 다시 작성 가능한지 검사한다.
- 코스에 포함된 상점의 방문 상태 저장·해제·멱등성을 검사한다.
- 비공개 코스 권한과 코스에 없는 상점을 거부하는지 검사한다.

### 프론트엔드

- 미방문 버튼이 BottomSheet를 여는지 검사한다.
- 닫기, 방문만 기록, 로그 작성하기 세 경로를 검사한다.
- 로그 작성하기는 저장 성공 뒤 올바른 상점 작성 경로로 이동하는지 검사한다.
- 활성 버튼을 다시 누르면 비활성화되는지 검사한다.
- 실패 시 상태 복원과 오류 안내를 검사한다.
- 320px, 390px, 480px와 키보드·포커스 동작을 Storybook에서 검사한다.

## 프로젝트 구조와 코드 스타일

- 공용 요청·응답 타입과 오류 코드는 `packages/shared`에 둔다.
- 백엔드는 라우터 → 컨트롤러 → 서비스 → 모델 경계를 유지한다.
- 모델, 서비스와 검증 테스트는 해당 도메인 파일 가까이에 둔다.
- 프론트엔드는 기존 React Query API 계층과 공용 `BottomSheet`, `Button`을 재사용한다.
- 새 함수에는 구현을 읽어주는 설명이 아니라 목적을 밝히는 짧은 주석을 단다.
- 방문 상태 API는 `setCourseShopVisited`, `unsetCourseShopVisited`처럼 저장 부수 효과가 이름에 드러나게 한다.

## 구현 순서

1. 방문 로그 날짜 키·중복 오류 계약·백필 검사
2. CourseShopVisit 모델과 방문 상태 API
3. 코스 상세 응답의 `isVisited` 연결
4. 코스 상점 버튼과 방문 로그 제안 BottomSheet
5. 코스에서 작성 화면 진입·완료 후 복귀
6. 상점 상세 CTA 문구 정리

## 경계

- 항상: API 경계 검증, DB 고유 인덱스, 로그인·코스 접근 권한, 실패 상태 복원을 함께 구현한다.
- 먼저 확인: 기존 활성 중복 로그를 자동으로 삭제하거나 병합하는 작업.
- 하지 않음: 방문 체크 해제에 따른 로그 삭제, 로그 작성 완료에 따른 Pick 상태 변경, 위치 기반 방문 인증.

## 완료 기준

- 같은 사용자·상점·한국 날짜의 활성 방문 로그가 하나만 존재한다.
- 코스의 각 상점 방문 상태가 사용자별로 독립 저장된다.
- 미방문 버튼은 BottomSheet를 열고 두 선택 모두 방문 상태를 저장한다.
- `로그 작성하기`만 방문 로그 작성 화면으로 이동한다.
- 활성 버튼을 다시 누르면 방문 상태만 해제된다.
- 새로고침 뒤에도 방문 상태가 유지된다.
- 관련 테스트·빌드·린트와 모바일 접근성 검증을 통과한다.

## 열린 질문

없음. 기존 중복 데이터가 발견될 때의 정리 방식만 실제 결과를 확인한 뒤 별도 승인받는다.
