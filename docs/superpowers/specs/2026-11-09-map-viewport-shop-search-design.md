# 지도 영역 상점 재검색 설계

## 의도

현재 지도 마커와 바텀시트 목록은 하나의 무한 스크롤 결과를 함께 사용한다. 그래서 사용자가 목록의 다음 페이지를 불러오기 전에는 아직 조회되지 않은 상점의 마커도 지도에 나타나지 않는다.

지도 마커 조회를 목록 페이지네이션에서 분리한다. 사용자가 지도를 이동하거나 확대·축소한 뒤 `이 지역에서 재검색`을 선택하면 현재 지도 영역의 상점을 다시 조회한다. 바텀시트는 같은 검색 영역의 목록을 계속 무한 스크롤로 제공하되, 목록 페이지를 추가로 불러오는 동작이 마커 수를 바꾸지는 않게 한다.

## 목표

- 지도에 처음 진입하면 초기 지도 영역의 모든 상점 마커를 목록 스크롤과 무관하게 표시한다.
- 지도를 이동하거나 확대·축소해도 즉시 연속 요청하지 않고 `이 지역에서 재검색` 버튼을 표시한다.
- 버튼을 선택하면 현재 지도 영역을 새 검색 영역으로 확정하고 마커와 목록을 함께 갱신한다.
- 바텀시트 목록의 무한 스크롤은 유지한다.
- 검색어와 태그 필터는 목록과 마커에 동일하게 적용한다.
- 새 요청 중에는 기존 마커를 유지해 지도가 비거나 깜빡이지 않게 한다.

## 비목표

- 마커 클러스터링 UI는 이번 범위에 포함하지 않는다.
- 사용자 위치 권한과 현재 위치 이동 동작은 바꾸지 않는다.
- 상점 상세 카드와 `shopId` URL 상태는 바꾸지 않는다.
- 현재 `내 픽` 목록 필터가 로드된 데이터에만 적용되는 문제는 이번 작업에서 확장하지 않는다.

## 피해야 할 결과

- 지도를 드래그하는 동안 API 요청이 연속으로 발생하면 안 된다.
- 목록의 다음 페이지를 불러올 때 마커가 추가되거나 제거되면 안 된다.
- 새 마커 요청이 실패했을 때 기존 마커를 지우면 안 된다.
- 지도 화면에 없는 상점을 모두 미리 불러오면 안 된다.
- 마커 조회를 위해 목록 카드에만 필요한 이미지·주소·태그 집계 데이터를 내려주면 안 된다.

## 현재 구조와 제약

- `MapScreen`은 `useInfiniteShops`의 모든 페이지를 합쳐 같은 `visibleShops`를 지도와 바텀시트에 전달한다.
- 첫 페이지 크기는 10개이므로 최초 마커도 최대 10개다.
- `NaverMapCanvas`는 지도 생성과 마커 렌더링을 담당하지만 현재 지도 경계 변경을 부모에게 알리지 않는다.
- 기존 `GET /api/shops`는 중심점·반경 조회를 지원하지만 페이지네이션된 목록 카드 데이터를 반환한다.
- MongoDB 상점 모델은 위치 검색용 `2dsphere` 인덱스를 이미 사용한다.
- 지도는 대한민국 상점 탐색용이므로 날짜 변경선을 가로지르는 경계는 다루지 않는다.

## 검토한 방식

### 선택: 지도 전용 영역 조회 API

현재 지도 화면의 남서·북동 좌표로 별도 마커 API를 호출한다. 목록용 API와 마커용 API가 같은 확정 영역과 필터를 사용하되 서로 다른 응답을 받는다.

장점은 화면에 보이는 상점을 정확히 조회하고, 마커에 필요한 작은 데이터만 전달하며, 목록 페이지네이션과 완전히 분리할 수 있다는 점이다. 프론트엔드·공용 계약·백엔드를 함께 수정해야 하지만 상점 수가 늘어나도 책임이 명확하다.

### 제외: 기존 상점 목록 API에 중심점과 반경 전달

기존 계약을 재사용할 수 있어 빠르다. 하지만 직사각형인 지도 화면과 원형 반경이 맞지 않고, 마커에 불필요한 목록 카드 데이터와 페이지네이션 문제가 남는다.

### 제외: 목록의 모든 페이지를 백그라운드에서 조회

백엔드 변경은 적지만 지도 밖 상점까지 전부 내려받는다. 상점이 늘수록 첫 화면이 느려지고 데이터 사용량도 계속 커지므로 사용하지 않는다.

## API 계약

### 지도 마커 조회

`GET /api/shops/map`

요청 쿼리:

- `southWestLat`, `southWestLng`: 지도 남서쪽 좌표
- `northEastLat`, `northEastLng`: 지도 북동쪽 좌표
- `keyword`: 선택 검색어
- `tagKeys`: 선택 태그 목록

응답 항목:

- `id`
- `name`
- `latitude`
- `longitude`
- `isLiked`

선택 상점 카드는 기존 상세 API로 조회하므로 마커 응답에 이미지와 상세 정보를 포함하지 않는다. `isLiked`는 현재 `내 픽` 마커 필터 동작을 유지하기 위해 포함한다.

지도 마커는 한 요청에서 최대 200개로 제한한다. 제한을 넘기면 응답에 `isTruncated: true`를 포함하고 프론트엔드는 `상점이 많아요. 지도를 확대해 주세요.` 안내를 표시한다. 200이라는 값은 서버 정책 상수로 관리한다. 제한된 결과는 `createdAt` 내림차순과 `_id` 내림차순으로 정렬해 같은 데이터에서는 항상 같은 상점을 반환한다.

### 목록 조회

기존 `GET /api/shops`에 동일한 네 경계 좌표를 선택 쿼리로 추가한다. 네 값은 모두 함께 전달해야 한다. 경계가 있으면 목록도 해당 지도 영역 안의 상점만 페이지 단위로 반환한다.

지도 전용 응답과 목록 응답은 `@sopum-map/shared`에 각각 명시한다. 두 API는 경계와 필터 계약을 공유하지만 반환 타입은 합치지 않는다.

## 백엔드 동작

- 네 경계 좌표의 범위와 동시 존재 여부를 Zod에서 검증한다.
- 남서 좌표가 북동 좌표보다 작아야 한다.
- 좌표로 닫힌 GeoJSON 사각형을 만들고 `location`의 `2dsphere` 인덱스로 영역 안의 활성 상점을 조회한다.
- 검색어와 태그 필터는 기존 상점 필터 규칙을 재사용한다.
- 로그인 사용자는 조회된 상점 ID를 한 번에 조회해 `isLiked`를 계산한다.
- 마커 API는 좋아요 수와 방문 로그 수를 집계하지 않는다.
- 목록 API의 기존 페이지네이션과 정렬은 유지한다.

## 프론트엔드 상태와 흐름

지도 경계는 다음 세 값으로 나눈다.

- `draftBounds`: 사용자가 현재 보고 있는 지도 영역
- `requestedBounds`: 사용자가 재검색을 선택해 현재 요청 중인 영역
- `searchedBounds`: 마커와 목록 조회가 모두 성공해 현재 화면에 표시 중인 영역

### 첫 진입

1. 네이버 지도 SDK가 준비되고 지도가 생성된다.
2. 지도의 현재 경계를 읽어 `draftBounds`와 `requestedBounds`를 함께 설정한다.
3. `requestedBounds`로 마커 조회와 첫 목록 페이지 조회를 시작한다.
4. 두 조회가 성공하면 해당 영역을 `searchedBounds`로 확정한다.
5. 최초 진입에는 이전 데이터가 없으므로 마커와 목록의 성공·오류 상태를 각각 표시한다.

### 지도 이동과 재검색

1. 지도 `idle` 이벤트에서 이동이 끝난 현재 경계를 `draftBounds`에 저장한다.
2. `draftBounds`와 `searchedBounds`가 다르면 지도 위에 `이 지역에서 재검색` 버튼을 표시한다.
3. 버튼을 선택하면 `draftBounds`를 `requestedBounds`로 설정한다.
4. 새 경계가 React Query 키에 반영되어 마커와 목록 첫 페이지를 함께 다시 조회한다.
5. 두 조회가 모두 성공하면 새 결과를 함께 표시하고 `requestedBounds`를 `searchedBounds`로 확정한다.
6. 확정이 끝나면 재검색 버튼을 숨긴다.

좌표의 아주 작은 소수점 차이로 버튼이 반복 표시되지 않도록 경계 좌표를 일관된 정밀도로 정규화한다. 정밀도 값은 지도 영역 도구 한곳에서 관리한다.

### 요청 중과 실패

- 재검색 요청 중에는 기존 마커를 유지한다.
- 버튼은 `검색 중...`으로 바꾸고 중복 선택을 막는다.
- 목록도 기존 검색 영역의 결과를 유지하면서 새 영역을 조회 중임을 표시한다.
- 마커와 목록이 모두 성공하기 전에는 어느 한쪽만 새 영역 결과로 교체하지 않는다.
- 둘 중 하나가 실패하면 기존 마커와 목록을 함께 유지하고 재검색 버튼을 다시 활성화한다.
- 성공한 새 응답은 React Query 캐시에 남겨 재시도 비용을 줄이되, 실패한 요청까지 성공한 뒤 화면에 함께 반영한다.
- 마커 오류와 목록 오류는 사용자가 원인을 구분할 수 있게 별도로 안내한다.

### 필터 변경

검색어 또는 태그가 변경되면 현재 `draftBounds`를 `requestedBounds`로 설정하고 별도 버튼 선택 없이 마커와 목록을 다시 조회한다. 두 조회가 성공하면 새 필터와 영역을 함께 확정한다. 사용자가 필터 결과를 즉시 기대하기 때문이다.

### 프로그램에 의한 지도 이동

마커를 선택해 `panTo`가 실행되는 경우에는 사용자가 탐색 영역을 바꾼 것으로 취급하지 않는다. 해당 이동 뒤 발생하는 `idle` 한 번은 재검색 필요 상태로 만들지 않는다. 사용자가 이후 직접 지도를 움직이면 다시 버튼을 표시한다.

## 컴포넌트와 책임

- `NaverMapCanvas`: 지도 생성, 현재 경계 읽기, `idle` 알림, 마커 렌더링
- 지도 영역 상태 훅: `draftBounds`, `requestedBounds`, `searchedBounds`, 재검색 필요 여부와 확정 동작
- 마커 React Query 훅: 확정 경계와 필터로 지도 전용 API 조회
- `MapScreen`: 목록과 마커 조회를 조합하고 버튼·오류·잘림 안내 상태 연결
- `MapShopListSheet`: 확정 경계의 페이지 목록만 렌더링하고 기존 무한 스크롤 유지

마커 타입과 목록 카드 타입은 분리한다. 선택 상점 상세는 기존 `useShopDetail`을 유지한다.

## 테스트와 확인

### 공용 계약·백엔드

- 네 경계 좌표가 모두 있을 때만 요청을 허용한다.
- 잘못된 좌표 범위와 뒤집힌 남서·북동 좌표를 거부한다.
- 영역·검색어·태그 조건이 함께 적용된다.
- 비로그인 응답은 `isLiked: false`, 로그인 응답은 실제 좋아요 상태를 반환한다.
- 마커 응답이 최대 개수와 `isTruncated` 정책을 지킨다.
- 목록 API가 같은 경계에서 페이지네이션을 유지한다.

### 프론트엔드

- 첫 지도 준비 시 마커와 목록을 자동 조회한다.
- 지도 이동만으로는 새 API 요청이 발생하지 않는다.
- 이동 후 재검색 버튼이 나타난다.
- 버튼 선택 시 마커와 목록 쿼리 키가 새 경계로 바뀐다.
- 목록의 다음 페이지를 불러와도 마커가 바뀌지 않는다.
- 재검색 중 기존 마커가 유지되고 중복 요청이 막힌다.
- 마커와 목록이 모두 성공한 뒤에만 새 영역 결과가 함께 표시된다.
- 하나라도 실패하면 기존 마커·목록과 다시 시도할 수 있는 버튼이 남는다.
- 검색어·태그 변경 시 현재 영역으로 즉시 다시 조회한다.
- 프로그램에 의한 `panTo`는 재검색 버튼을 만들지 않는다.
- 320px, 390px, 480px에서 버튼이 검색 헤더·마커·바텀시트와 겹치지 않는다.
- 키보드로 재검색 버튼에 접근할 수 있고 로딩·오류 상태가 보조 기술에 전달된다.

## 구현자가 결정할 수 있는 세부 사항

- 경계 좌표 정규화의 정확한 소수점 자릿수
- 재검색 버튼의 정확한 시각 토큰과 지도 위 위치
- 마커 조회 오류 안내를 토스트가 아닌 현재 화면 상태 UI 중 어디에 둘지
- 영역 비교와 GeoJSON 사각형 생성을 위한 작은 순수 함수의 파일 배치
