# 방문 로그 UX/UI 및 서비스 설계

## 목적

기존 후기를 `방문 로그`로 재정의한다. 방문 로그는 사용자의 개인 방문 아카이브이면서 상점 상세에 공개되는 방문 경험 정보다. Pick이나 Course 사용 여부와 관계없이 로그인 사용자는 같은 상점에 여러 번 기록할 수 있다.

## 범위

### 1차 핵심 범위

- 서비스 화면의 `후기` 명칭을 `방문 로그`로 변경
- 방문 로그 작성, 상점별 공개 목록, 내 방문 로그 목록
- 방문일과 방문 경험 태그 필수 입력
- 선택적인 사진과 글
- 본인 로그 수정 및 소프트 삭제
- 사진 유무에 따른 카드 표현
- 상점 상세의 작성 CTA와 방문 로그 미리보기 개편
- 마이페이지 진입 경로

### 후속 범위

- S3 이미지 업로드와 고아 이미지 정리
- 홈의 방문 로그 요약
- 누적 로그 기반 등급과 쿼카 보상
- Pick과 Course에서 작성 화면으로 연결
- 신고와 운영자 콘텐츠 관리

### 제외 범위

- 댓글과 메시지
- 방문 지역 통계
- 비공개 로그
- 위치 기반 방문 인증
- 방문 로그 전용 하단 탭
- 소품 컬렉션

## 핵심 정책

- 모든 방문 로그는 공개다. 작성 화면에 공개 안내를 표시한다.
- 방문 상점, 방문일, 태그 1~8개가 필수다.
- 사진과 글은 선택 사항이다. 태그만 선택한 로그도 정상 기록으로 취급한다.
- 방문일 기본값은 오늘이며 미래 날짜는 허용하지 않는다.
- 같은 사용자가 같은 상점에 여러 로그를 남길 수 있다.
- 삭제는 `status: deleted`로 처리하고 공개 목록과 보상 계산에서 제외한다.
- 동일 사용자·상점·방문일의 로그 중 하루 1개만 향후 보상 실적으로 인정한다. 기록 생성 자체는 제한하지 않는다.

## 용어와 태그 표시 규칙

코드와 API에서는 `VisitLog`, 사용자 화면에서는 `방문 로그`를 사용한다.

태그의 기준은 `@sopum-map/shared`의 `TAG_DEFINITIONS`다. 별도 태그 ID나 화면 전용 문자열 목록을 만들지 않고 `TagKey`를 저장한다.

작성·상점 상세·내 방문 로그는 모두 `TAG_DEFINITIONS.label`을 표시한다. 같은 키가 화면마다 다른 문구로 보이지 않게 단일 라벨을 사용한다.

새 방문 로그와 상점 태그 통계에는 현재 허용된 24개 활성 태그만 사용한다. 폐기된 태그 키는 데이터 정리 스크립트로 제거한다.

## 작성 화면 태그 UX

지도 태그 필터와 같은 그룹 제목, 작은 둥근 선택 칩, 활성 색상 표현을 사용한다.

전체 태그가 길기 때문에 그룹별로 다음 방식으로 접는다.

1. `product`, `mood`, `experience`를 각각 질문형 제목과 설명으로 구분한다.
2. 각 그룹은 처음 6개를 표시하고 `더보기`와 `접기`로 나머지를 전환한다.
3. 선택 결과를 별도 영역에 복제하지 않고 선택한 칩 자체의 색만 변경한다.
4. 전체 태그에서 최소 1개, 최대 8개를 선택한다. 세 그룹을 모두 선택하도록 강제하지 않는다.
5. 최대 8개에 도달하면 선택되지 않은 태그를 비활성화하고 선택 개수를 표시한다.
6. `aria-expanded`, `aria-pressed`를 사용하고 펼침 뒤 새 영역으로 포커스를 강제로 이동하지 않는다.

## 화면별 정보 구조

### 방문 로그 작성

작성 경로는 `/shops/:shopId/visit-logs/new`를 사용한다. 기존 `/reviews/new` 주소는 저장된 링크와 브라우저 기록 호환을 위해 새 경로로 교체 이동한다.

작성 화면은 한 페이지에 모든 입력을 쌓지 않고 3단계로 진행한다.

1. 방문 상점과 방문일: 상점 상세·상점 카드·코스에서 진입하면 해당 상점을 미리 선택하고, 마이페이지에서 진입하면 상점을 검색해 선택한다. 방문일은 한국어 바텀시트 달력에서 고르며 미래 날짜를 비활성화한다. 상점과 방문일이 모두 있어야 다음 단계로 이동한다.
2. 태그 선택: `어떤 소품이 있었나요?`, `어떤 분위기였나요?`, `방문 경험은 어땠나요?` 세 질문에서 태그를 고른다. 전체에서 하나 이상 선택해야 다음 단계로 이동한다.
3. 사진과 방문 내용: 사진과 최대 1,000자의 글은 선택 사항이다. 공개 안내와 기록 동기를 보여주고 중복 제출을 막는다.

등록 성공 시 `방문 로그가 기록됐어요!`를 안내한 뒤 해당 상점 상세로 이동한다. S3 도입 전에는 이미지 없는 로그 작성을 먼저 완성한다.

### 상점 상세

상점 기본정보 바로 아래에 CTA를 배치한다.

- 최초 기록 전: `내 방문 로그에 기록하기`
- 기존 기록이 있으면: 방문 횟수와 최근 방문일, `다시 방문 기록하기`

하단 제목은 `이곳의 방문 로그 N개`로 변경한다. 상점 상세는 전체 피드가 아니라 일부 미리보기이므로 정보량이 풍부한 로그를 우선한다.

우선순위는 다음처럼 고정한다.

1. 사진이 있는 로그
2. 사진은 없지만 글이 있는 로그
3. 태그만 있는 로그

같은 단계에서는 `visitedAt`, `createdAt`, `_id` 내림차순으로 정렬한다. 사진이 없는 로그는 빈 이미지나 기본 이미지를 넣지 않고 태그와 글 중심의 컴팩트 카드로 표시한다. 전체 목록 링크는 별도로 제공한다.

### 내 방문 로그

마이페이지의 `방문 로그` 메뉴로 진입한다. 기본 정렬은 개인 기록의 시간 흐름을 보존하기 위해 최신 방문일순이며, 상점 상세의 정보량 우선 정렬을 적용하지 않는다.

- 상단: 누적 로그 수, 방문한 고유 상점 수, 새 기록 작성 버튼
- 사진 로그: 큰 이미지, 상점명, 방문일, `label` 태그, 글, 수정·삭제 메뉴
- 사진 없는 로그: 상점명, 방문일, `label` 태그, 글을 담은 컴팩트 카드
- 빈 상태: 첫 방문 로그 작성 경로
- 등급과 캐릭터는 2차 범위에서 추가

### 홈·Pick·Course

- 홈 요약은 1차 작성·조회 흐름이 안정된 다음 추가한다.
- Pick은 로그 저장 후 자동으로 방문 완료 상태로 바꾸지 않는다.
- Course는 실제 방문한 상점만 개별 기록하게 하며 일괄 작성은 후순위다.

## 데이터 모델 방향

`VisitLog`의 1차 필드는 다음과 같다.

| 필드 | 형태 | 정책 |
| --- | --- | --- |
| `userId` | ObjectId | 로그인 사용자 |
| `shopId` | ObjectId | 존재하는 활성 상점 |
| `visitedAt` | Date | 오늘 이하 |
| `selectedTagKeys` | `TagKey[]` | 활성 태그 1~8개, 중복 금지 |
| `content` | string/null | 선택, trim, 최대 1,000자 |
| `imageKeys` | string[] | S3 도입 전 빈 배열, 최대 5개 |
| `status` | active/deleted | 기본 active, 소프트 삭제 |
| timestamps | Date | 생성·수정 시각 |

기존 `imageUrls` 데이터가 있다면 읽기 호환을 유지하고, S3 도입 시 새 저장은 `imageKeys`를 사용한다. API 응답의 `imageUrls`는 CDN 또는 S3 공개 경로를 조합한 표시 URL로 유지한다.

상점별 공개 조회 인덱스는 `shopId + status + visitedAt`, 내 목록은 `userId + status + visitedAt`을 기준으로 한다. 정보량 우선 정렬은 사진·글 존재 여부를 계산하는 aggregation 또는 저장된 정렬 보조값으로 구현하되, 초기에는 aggregation을 우선하여 중복 상태 저장을 피한다.

## API 방향

| Method | Endpoint | 역할 |
| --- | --- | --- |
| POST | `/shops/:shopId/visit-logs` | 이미지 없는 로그부터 작성 |
| GET | `/shops/:shopId/visit-logs` | 상점 상세 공개 목록 |
| GET | `/me/visit-logs` | 내 방문 로그 |
| PATCH | `/visit-logs/:visitLogId` | 본인 로그 수정 |
| DELETE | `/visit-logs/:visitLogId` | 본인 로그 소프트 삭제 |
| POST | `/uploads/visit-log-images/presign` | 후속 S3 업로드 URL 발급 |

작성 요청은 `visitedAt`, `selectedTagKeys`, `content`, `imageKeys`를 받는다. 백엔드는 상점 존재 여부, 미래 방문일, 활성 태그, 태그 수와 중복, 이미지 키 소유권을 검증한다.

목록 응답은 태그 키를 유지한다. 프론트엔드는 공용 정의에서 위치에 맞는 라벨을 선택한다. 이렇게 하면 같은 데이터가 화면마다 다른 길이의 라벨을 안전하게 사용할 수 있다.

## 오류와 예외 상태

- 비로그인 작성 시 로그인 안내
- 삭제·비활성 상점 작성 차단
- 태그 미선택, 8개 초과, 중복 또는 비활성 태그 차단
- 미래 방문일 차단
- 등록 중 버튼 비활성화
- API 실패 시 입력값을 유지하고 재시도 안내
- 이미지 업로드 일부 실패 시 성공한 이미지와 실패한 이미지를 구분
- 직접 URL 접근과 화면 뒤로가기 모두 상점 상세로 안전하게 복귀

## 구현 순서

1. 공용 타입, 모델, 검증과 이미지 없는 작성 API
2. 실제 상점 정보·상점 검색·3단계 입력을 사용하는 작성 화면 연동
3. 상점 상세 CTA, 방문 로그 명칭, 정보량 우선 미리보기와 컴팩트 카드
4. 내 방문 로그 목록, 수정과 삭제
5. S3 presigned URL 업로드와 이미지 키 검증·정리
6. 홈 요약
7. 보상 인정 계산, 등급과 쿼카 캐릭터
8. Pick과 Course 연결

각 단계는 공용 계약, 백엔드 테스트, 프론트 단위·Storybook 테스트, 빌드와 린트를 통과한 뒤 별도 커밋으로 완료한다.

## 기존 설계와의 차이

- 기존 이슈의 `selectedTagIds`는 실제 공용 태그 구조에 맞춰 `selectedTagKeys`로 변경한다.
- 기존 작성 화면의 하드코딩 태그와 상점 fixture를 제거한다.
- 기존 `후기` 명칭은 `방문 로그`로 변경한다.
- 닫힌 UI 이슈는 당시 구현 기록으로 유지하고 새 요구사항은 열린 상위·연동 이슈에서 관리한다.
- 상점 상세와 내 방문 로그는 목적이 다르므로 정렬 기준도 다르게 둔다.
- 사진 없는 로그에 기본 이미지를 넣지 않고 전용 컴팩트 카드를 사용한다.
