# Frontend UI Screens Design

## Goal

Figma의 모바일 디자인을 기준으로 열려 있는 프론트엔드 UI 이슈 8개를 구현한다. 각 이슈는 독립적으로 검토할 수 있는 PR로 제공하고 API 연동 전에도 임시 데이터로 전체 흐름을 확인할 수 있게 한다.

## Scope and order

1. `#21` 온보딩 페이지 UI
2. `#68` 홈 페이지 UI
3. `#30` 지도 페이지 UI
4. `#33` 내 픽 페이지 UI
5. `#36` 상점 상세 페이지 UI
6. `#39` 후기 작성 페이지 UI
7. `#42` 코스 상세 페이지 UI
8. `#45` 마이페이지 UI

API 호출, 실제 인증, 서버 데이터 변경은 범위에서 제외한다. 네이버 지도 SDK의 지도 엔진과 임시 좌표 기반 마커는 `#30`에 포함한다. 버튼과 필터 등 화면 안에서 확인할 수 있는 클라이언트 상호작용도 포함한다.

## Delivery strategy

8개의 PR을 스택으로 구성한다. `#21` 브랜치는 `dev`에서 시작하고 이후 브랜치는 직전 UI 브랜치에서 분기한다. 각 PR의 기준 브랜치도 직전 브랜치로 지정하여 해당 이슈의 변경만 보이게 한다. PR은 위 순서로 병합하며 앞 PR이 `dev`에 병합되면 다음 PR의 기준 브랜치를 `dev`로 변경할 수 있다.

브랜치 이름은 `feat/<issue-number>/<short-name>-ui` 형식을 사용한다. 각 PR은 저장소의 `.github/pull_request_template.md`를 따르고 해당 이슈를 `Closes #<number>`로 연결한다.

사용자가 만들어 둔 `.agents/`, `AGENTS.md`, `MEMORY.md`는 UI PR에 포함하지 않는다. 명세와 구현 계획은 첫 UI PR에 포함한다.

## Shared visual system

- Figma의 393px 화면을 중심으로 구현하되 320px, 390px, 480px에서 자연스럽게 늘어나게 한다.
- 앱 프레임의 기존 최대 너비 480px를 유지한다.
- Pretendard와 기존 CSS 색상·타이포그래피 토큰을 우선 사용한다.
- Figma의 장식 글꼴을 사용할 수 없는 곳은 Pretendard 굵기와 자간으로 계층을 재현한다.
- 상단 상태바 이미지는 운영 UI가 아니므로 구현하지 않는다. 브라우저의 안전 영역과 실제 콘텐츠만 구현한다.
- 원격 Figma 임시 asset URL은 사용하지 않는다. 저장소의 기존 이미지나 재사용 가능한 로컬 asset을 사용하고, 없는 장식은 CSS 또는 단순 도형으로 표현한다.
- 터치 대상에는 접근 가능한 이름과 키보드 포커스 상태를 제공한다.
- 새로 작성하는 모든 함수 바로 위에는 목적을 설명하는 짧은 주석을 둔다.

## Shared components

기존 `Button`, `Badge`, `SearchInput`, `FilterChipGroup`, `ShopCard`, `ShopBannerCarousel`, `CourseListItem`을 우선 재사용한다. 화면 구현 중 공통으로 필요한 아래 단위를 추가한다.

- `BottomNavigation`: 홈, 지도, 내 픽, 마이페이지 4개 메뉴와 현재 경로 표시
- `PageHeader`: 뒤로가기, 제목, 선택적 우측 액션
- `BottomSheet`: dim 처리, 제목, 콘텐츠, 액션, 외부 클릭·Escape 닫기
- `Modal`: 제목, 본문, 액션, 외부 클릭·Escape 닫기
- `Textarea`: label, 도움말, 오류, 글자 수, disabled와 readOnly 상태
- `EmptyState`와 `ErrorState`: 화면별 안내 문구와 선택적 액션
- `ShopCompactCard`: 지도 목록, 내 픽, 코스 등 좁은 목록에서 재사용

공통 컴포넌트는 처음 필요한 UI 이슈에서 추가한다. 이후 PR은 앞 브랜치의 컴포넌트를 재사용한다.

## Screen designs

### #21 Onboarding

중앙 캐릭터 또는 브랜드 이미지, 서비스명, 핵심 메시지, `시작하기` 버튼, 로그인 이동 링크를 한 화면에 배치한다. 은은한 녹색 배경 장식을 CSS로 만들고 캐릭터 영역에는 움직임 감소 설정을 존중하는 가벼운 부유 애니메이션을 적용한다. 시작하기와 로그인 링크는 로그인 페이지로 이동한다. 온보딩 완료 저장은 `#22` 범위이므로 저장하지 않는다.

### #68 Home

오늘의 큐레이션, 카테고리, 카테고리별 상점, 추천 산책 코스, 브랜드 문구 순서로 구성한다. 큐레이션과 상점 목록은 터치 가능한 가로 스크롤을 사용한다. 카테고리 선택은 로컬 상태로 표시하며 임시 데이터 목록을 바꾼다. 화면에는 로딩·빈 상태·오류 상태를 개별 컴포넌트로 표현할 수 있는 구조를 둔다. 하단에는 4개 메뉴 내비게이션을 표시한다.

### #30 Map

네이버 지도 JavaScript SDK로 실제 지도 엔진을 표시한다. 브라우저에 공개 가능한 네이버 지도 Client ID는 `NEXT_PUBLIC_NAVER_MAP_CLIENT_ID` 환경변수로 관리한다. SDK 스크립트의 중복 로딩을 막고 준비·성공·실패 상태를 명확하게 처리하는 지도 래퍼를 둔다.

검색창, 가로 카테고리 필터, 커스텀 상점 마커, 현재 위치 버튼과 상점 목록 바텀시트를 지도 위에 배치한다. 임시 좌표와 상점 데이터로 마커와 목록을 연결하고, 검색어와 카테고리는 로컬 상태로 두 영역을 함께 필터링한다. 마커를 선택하면 연결된 상점을 강조하고 상점 항목은 상세 페이지로 이동한다. 필터 결과가 없으면 바텀시트 안에 빈 상태를 표시한다.

Client ID가 없거나 SDK 로딩이 실패하면 빈 지도 모양으로 오해할 수 있는 정적 이미지를 표시하지 않는다. 설정 또는 로딩 문제임을 알려주는 대체 화면과 다시 시도 동작을 제공한다. 실제 상점 API, 서버 기반 검색·필터, 사용자 위치 기반 조회는 `#31`에 남긴다.

### #33 Picks

좋아요한 상점과 폴더를 탭으로 구분한다. 좋아요 탭은 상점 카드 목록을 표시한다. 폴더 탭은 폴더 카드, 폴더 생성 액션, 선택한 폴더의 상점과 메모, 코스 만들기 버튼을 표시한다. 폴더 생성은 재사용 가능한 모달로 입력 흐름만 제공하고 새 폴더를 로컬 상태에 추가한다. 빈 폴더에는 별도 빈 상태를 표시한다.

### #36 Shop detail

대표 이미지, 뒤로가기·좋아요·제보 액션, 상점명·카테고리·태그, 주소와 영업 정보, 외부 링크, 위치 프리뷰, 방문 후기 목록을 세로 흐름으로 구성한다. 좋아요는 로컬 상태로 전환한다. 내 픽 추가는 바텀시트, 정보 수정 제보는 바텀시트와 완료 모달을 사용한다. 후기 작성 버튼은 해당 상점의 후기 작성 경로로 이동한다.

### #39 Visit review

상점 요약, 방문일, 방문 태그, 한 줄 후기, 이미지 첨부 프리뷰, 취소와 완료 버튼을 순서대로 제공한다. 후기 입력에는 공통 `Textarea`를 사용한다. 브라우저의 파일 선택과 로컬 미리보기를 제공하되 업로드는 하지 않는다. 필수값이 없으면 각 입력과 안내 영역에 오류를 표시한다.

### #42 Course detail

코스명, 설명, 지역·공개 여부·작성자 정보와 방문 순서가 있는 상점 목록을 표시한다. 상점 항목은 상세 페이지로 이동한다. 네이버지도 액션은 외부 링크로 표현한다. 내 코스라는 임시 조건에서 수정·삭제 버튼을 표시하고 삭제는 확인 모달로 처리한다. 상점이 없는 상태도 별도로 제공한다.

### #45 My page

프로필 카드와 프로필 수정 버튼, 좋아요·내 픽·코스·방문 기록·제보 내역 메뉴를 제공한다. 각 메뉴는 준비된 실제 경로 또는 설명 가능한 임시 경로로 연결한다. 로그아웃은 확인 모달을 사용한다. 로그인 여부는 임시 상태로 전환할 수 있게 구성하고 비로그인 상태에서는 로그인 안내와 이동 버튼을 표시한다.

## Data and routing

화면 전용 임시 데이터는 해당 기능 가까이에 타입과 함께 둔다. 여러 화면에서 공유하는 상점·코스 fixture만 별도 파일로 분리한다. API 응답처럼 생긴 비동기 계층을 만들지 않고 화면이 필요로 하는 표시 모델만 사용한다.

예정 경로는 다음과 같다.

- `/onboarding`
- `/`
- `/map`
- `/picks`
- `/shops/[shopId]`
- `/shops/[shopId]/reviews/new`
- `/courses/[courseId]`
- `/me`

## Error and empty states

UI 이슈에서는 네트워크 요청을 만들지 않지만, 이후 API 연결에서 구조를 다시 만들지 않도록 모든 데이터 영역에 `loading`, `success`, `empty`, `error` 상태 계약을 둔다. 오류 상태는 컴포넌트와 Storybook 또는 테스트 fixture로 검증한다. 데이터 배열이 비어 있는 경우에는 빈 공간 대신 다음 행동을 안내하는 문구와 버튼을 표시한다. 이미지가 없거나 깨진 경우 기존 기본 상점 이미지를 사용한다.

초기 로딩은 최종 콘텐츠와 비슷한 크기의 스켈레톤으로 표현해 레이아웃 이동을 줄인다. 긴 텍스트, 누락된 선택 필드, 빈 태그, 깨진 이미지에서도 컴포넌트가 렌더링되도록 안전한 표시 모델과 폴백을 사용한다. 중복 제출과 연속 클릭을 막고 실패한 낙관적 변경은 이전 상태로 되돌릴 수 있게 설계한다.

주요 라우트에는 Next.js `error.tsx`를 두고, 홈의 큐레이션·추천 코스처럼 서로 독립된 데이터 섹션에는 더 작은 Error Boundary를 사용한다. 한 섹션의 렌더링 오류가 다른 섹션, 하단 내비게이션, 전체 앱으로 번지지 않게 한다. Error Boundary가 잡지 못하는 이벤트 핸들러와 비동기 요청 오류는 각 경계에서 따로 처리한다. 오류 fallback은 맥락을 유지하고 가능한 경우 다시 시도 동작을 제공한다.

## Testing and verification

- 상호작용이 있는 컴포넌트는 Vitest 또는 Storybook 테스트를 먼저 작성하고 실패를 확인한 뒤 구현한다.
- 네이버 지도 SDK 래퍼는 스크립트 중복 방지, 준비 상태, Client ID 누락과 로딩 실패 대체 화면을 테스트한다.
- 각 공통 컴포넌트는 기본, 활성, 비활성, 로딩, 빈 상태, 오류와 접근성 상태를 Storybook에서 확인한다.
- 데이터 기반 컴포넌트는 누락 필드, 긴 텍스트, 깨진 이미지와 섹션 Error Boundary fallback을 검증한다.
- 각 PR에서 프론트엔드 lint와 build를 실행한다.
- 브라우저에서 320px, 390px, 480px 너비를 확인하고 콘솔 오류와 주요 키보드 동작을 점검한다.
- `git diff --check`와 변경 파일 검토로 해당 이슈 밖의 파일이 섞이지 않았는지 확인한다.

## PR boundaries

각 PR은 연결된 이슈의 화면, 그 화면에서 처음 필요한 공통 컴포넌트, 관련 테스트·스토리만 포함한다. 후속 화면을 미리 구현하지 않는다. API 연결과 서버 변경은 포함하지 않는다. 스택의 선행 PR 변경이 후행 PR에 보이지 않도록 PR 기준 브랜치를 정확히 지정한다.
