# 공개 산책 코스 탐색 설계

## 의도

사용자가 소품지도가 만든 추천 코스와 다른 사용자가 공개한 코스를 홈에서 발견하고, `/courses`에서 지역과 정렬 기준을 바꿔 계속 탐색할 수 있게 한다.

홈은 매일 조금씩 달라지는 발견 공간으로 사용한다. `/courses`는 사용자가 최신 코스와 인기 코스를 직접 훑는 탐색 공간으로 사용한다.

## 현재 상태

- 홈의 `추천 산책 코스`는 `MOCK_COURSES` 3개를 표시한다.
- 공개 코스 목록을 조회하는 `GET /api/courses`가 없다.
- `/courses` 목록 페이지가 없다.
- 내 코스와 찜한 코스는 커서 기반 무한 스크롤을 사용한다.
- `CourseListItem`은 사진 콜라주, 제목, 설명과 태그만 표시한다.
- 코스에는 `isOfficialPick`과 대표 태그가 저장되어 있지 않다.

## 목표

- `recommended` 코스와 공개된 `user_created` 코스를 하나의 탐색 목록에 노출한다.
- 홈에 하루 동안 고정되는 추천 코스 3개를 표시한다.
- 홈의 3개는 가능한 한 서로 다른 지역에서 고른다.
- `/courses`에서 전체 또는 지역별 코스를 최신순과 인기순으로 탐색한다.
- 홈과 공개 목록에서 같은 코스 카드 표현을 사용한다.
- 사용자 공개 코스에 설정된 `소품지도 Pick`을 일관된 뱃지로 표시한다.
- 목록 조회가 항목 수만큼 추가 쿼리를 만드는 N+1 구조가 되지 않게 한다.

## 비목표

- 사용자별 취향이나 현재 위치를 반영한 개인화 추천
- 제목·작성자·상점 이름을 이용한 검색
- 운영자가 Pick을 선정하거나 해제하는 관리자 화면과 API
- 코스를 자동으로 Pick으로 선정하는 기능
- 코스 작성자가 대표 태그를 직접 편집하는 기능
- 익명 사용자에게 공개 코스를 개방하는 인증 정책 변경

## 노출 대상

탐색 가능한 공개 코스는 다음 두 종류다.

- `courseType: "recommended"`이며 공개 상태인 코스
- `courseType: "user_created"`이며 `isPublic: true`인 코스

추천 코스와 사용자 코스는 정렬과 홈 추천에서 같은 기준으로 경쟁한다. 특정 종류의 최소 노출 수를 보장하지 않는다.

추천 코스는 기존 정책대로 저장 데이터도 `isPublic: true`를 유지한다. 따라서 공개 목록 조회는 `isPublic: true`를 공통 조건으로 사용할 수 있다.

## 검토한 접근

### 홈 추천

1. 최신 코스와 최근 반응 코스를 섞은 후보에서 날짜별로 선택
   - 새로운 코스와 최근 다시 관심받는 코스가 함께 기회를 얻는다.
   - 기준이 단순하여 운영자와 사용자에게 설명하기 쉽다.
2. 최근 좋아요와 생성일을 하나의 가중 점수로 계산
   - 세밀하게 조절할 수 있지만 가중치가 자의적이고 결과를 설명하기 어렵다.
3. 전체 공개 코스에서 완전 무작위 선택
   - 다양성은 높지만 반응이 없거나 오래된 코스가 자주 노출될 수 있다.

1번을 선택한다.

### 공개 목록 정렬

1. 하나의 목록에서 최신순과 인기순을 전환
   - 코스 종류와 상관없이 같은 탐색 경험을 제공한다.
2. 추천 코스와 사용자 코스를 별도 탭으로 분리
   - 출처는 명확하지만 두 코스를 같은 기준으로 경쟁시킨다는 정책과 맞지 않는다.
3. 추천순 하나만 제공
   - 기준이 불명확하고 홈의 역할과 겹친다.

1번을 선택한다.

## 홈 추천 정책

### 후보 만들기

- 그날 한국 시간 자정을 후보 계산의 기준 시각으로 사용한다.
- 기준 시각 전에 생성된 최신 공개 코스 10개를 고른다.
- 기준 시각 직전 7일 동안 받은 좋아요 수가 많은 공개 코스 10개를 고른다.
- 추천 코스와 사용자 공개 코스에 같은 조건을 적용한다.
- 중복 코스는 한 번만 포함한다.
- 중복 제거로 20개가 되지 않거나 한 후보군이 부족하면 남은 후보군의 다음 코스로 보충한다.
- 공개 코스가 20개보다 적으면 존재하는 코스만 후보로 사용한다.

최근 좋아요 순위의 동률은 최근 좋아요 시각과 코스 ID 내림차순으로 고정한다. 최신 코스의 동률은 생성일과 코스 ID 내림차순으로 고정한다.

### 하루 동안 고정하기

- 한국 시간대의 날짜를 추천 시드로 사용한다.
- 날짜와 코스 ID로 결정적인 순서를 만든다.
- 모든 사용자에게 그날 같은 코스 3개를 반환한다.
- 사용자 ID나 개인 활동을 시드와 후보 선정에 사용하지 않는다.
- 후보 계산은 그날 자정 이전 데이터만 사용하므로 당일 생성된 코스와 당일 새 좋아요가 결과를 바꾸지 않는다.
- 서버가 재시작돼도 같은 날짜에는 같은 순서를 반환한다.
- 한국 시간 자정 이후에는 새 날짜의 순서를 사용한다.
- 홈 쿼리는 다음 한국 시간 자정까지 fresh 상태를 유지한다.
- 홈을 계속 열어 둔 사용자의 목록을 자정에 강제로 교체하지 않는다. 다음 화면 진입이나 브라우저 재활성화 때 새 날짜 결과를 조회한다.
- 선택된 사용자 코스가 비공개로 바뀌거나 삭제되면 공개 안전성이 하루 고정보다 우선한다. 해당 코스를 제외하고 같은 날짜 후보의 다음 코스로 채운다.

### 지역 다양성

- 날짜별 후보 순서를 앞에서부터 확인한다.
- 아직 선택하지 않은 `regionGroup`의 코스를 먼저 고른다.
- 서로 다른 지역의 코스가 3개보다 적으면 남은 후보 중 지역이 겹치는 코스로 자리를 채운다.
- 공개 코스가 3개보다 적으면 존재하는 수만 반환한다.

## `/courses` 목록 정책

### 필터와 정렬

- 기본 지역은 전체다.
- 지역 필터는 기존 `SHOP_REGION_GROUPS`와 `regionGroup` 값을 사용한다.
- 기본 정렬은 최신순이다.
- 사용자가 인기순으로 변경할 수 있다.
- 최신순은 `createdAt`, `_id` 내림차순이다.
- 인기순은 `likeCount`, `createdAt`, `_id` 내림차순이다.
- 필터와 정렬은 URL에 저장한다.

예시:

```text
/courses
/courses?regionGroup=mangwon
/courses?regionGroup=mangwon&sort=popular
```

상세 화면에서 뒤로 이동했을 때 URL을 통해 지역과 정렬 선택을 복원한다. 필터나 정렬이 바뀌면 첫 페이지부터 새로 조회한다.

### 페이지네이션

- 기존 내 코스 목록처럼 커서 기반 무한 스크롤을 사용한다.
- 최신순 커서는 생성일과 코스 ID를 포함한다.
- 인기순 커서는 좋아요 수, 생성일과 코스 ID를 포함한다.
- 응답 순서가 같을 때 페이지 사이에서 항목이 중복되거나 빠지지 않게 복합 정렬 값을 모두 커서에 넣는다.

## 카드 표시 정책

홈과 `/courses`가 같은 공개 코스 카드 컴포넌트를 사용한다.

```text
┌──────────────┬────────────────────────────────┐
│ 상점 사진     │ 코스 제목                       │
│ 콜라주        │ 코스 설명 · by 작성자            │
│ 최대 4장      │ [Pick] [지역] [태그1] [태그2]  ♡ 수 │
└──────────────┴────────────────────────────────┘
```

- 사진은 코스의 방문 순서가 빠른 상점부터 최대 4장의 대표 이미지를 사용한다.
- 이미지가 없거나 깨지면 기존 상점 기본 이미지를 사용한다.
- 설명이 없으면 작성자 앞의 구분점이 어색하게 남지 않게 작성자만 표시한다.
- `recommended` 코스의 작성자는 `by 소품지도`로 표시한다.
- 사용자 코스의 작성자는 `by {닉네임}`으로 표시한다.
- 탈퇴하거나 찾을 수 없는 사용자는 기존 정책대로 `알 수 없는 사용자`로 표시한다.
- 좋아요 수는 하트 아이콘과 함께 표시한다.
- 지역 뱃지는 `regionGroup`의 공용 라벨을 사용한다.
- 긴 제목, 설명, 작성자와 여러 뱃지는 320px에서도 사진 영역을 침범하지 않게 잘라내거나 줄바꿈한다.

### 대표 태그

대표 태그는 코스 문서에 저장하지 않고 포함된 상점 데이터로 계산한다.

- 모든 포함 상점의 `tagKeys`를 집계한다.
- 많은 상점에 등장한 태그부터 최대 2개를 선택한다.
- 등장 횟수가 같으면 공용 태그 상수 순서를 사용한다.
- 태그가 없으면 지역 뱃지만 표시한다.
- API는 화면 문구가 아니라 `TagKey` 값을 반환하고 프론트엔드가 공용 라벨을 표시한다.

## 소품지도 Pick

코스 문서에 `isOfficialPick: boolean`을 추가하고 기본값을 `false`로 둔다.

- Pick은 공개된 사용자 코스에만 의미가 있다.
- `recommended` 코스는 `by 소품지도`로 출처가 드러나므로 Pick 뱃지를 표시하지 않는다.
- `courseType: "user_created"`, `isPublic: true`, `isOfficialPick: true`일 때만 목록과 상세에서 뱃지를 표시한다.
- 사용자 코스를 비공개로 바꿀 때 `isOfficialPick`을 함께 `false`로 바꾼다.
- 코스를 삭제하면 문서와 함께 Pick 상태도 사라진다.
- 첫 버전에서는 운영자가 공개 사용자 코스만 대상으로 `mongosh`에서 값을 설정한다.
- 운영자 선정·해제 API, 화면과 감사 기록은 별도 이슈로 남긴다.

기존 문서에 `수행 주체와 시점 추적` 정책이 있으나 이번 범위에는 관리 기능이 포함되지 않는다. 따라서 이번 필드는 표시 기반만 제공하며, 정식 운영 도구를 만들 때 감사 정보를 함께 설계한다.

## 공용 API 계약

공개 목록과 홈 추천은 같은 항목 타입을 사용한다. 화면에 필요한 최소 데이터만 포함한다.

```ts
type PublicCourseListItem = Readonly<{
  id: string;
  courseType: CourseType;
  title: string;
  description: string | null;
  regionGroup: ShopRegionGroup;
  imageUrls: readonly string[];
  representativeTagKeys: readonly TagKey[];
  author: CourseAuthor;
  likeCount: number;
  isOfficialPick: boolean;
  createdAt: string;
}>;
```

구체적인 타입 이름은 기존 `packages/shared/src/course/`의 이름 규칙과 충돌하지 않게 구현 계획에서 확정한다.

### `GET /api/courses`

공개 코스 탐색 목록을 반환한다.

요청 쿼리:

```ts
type GetPublicCoursesQuery = Readonly<{
  regionGroup?: ShopRegionGroup;
  sort?: "latest" | "popular";
  cursor?: string;
  limit?: number;
}>;
```

- `sort` 기본값은 `latest`다.
- `limit` 기본값과 최댓값은 기존 코스 목록 정책을 따른다.
- 잘못된 지역, 정렬, 커서와 범위 밖의 limit은 Zod 경계에서 거부한다.
- 응답은 기존 `CourseCursorPage<PublicCourseListItem>` 형태를 재사용한다.

### `GET /api/courses/home`

그날의 홈 추천 코스를 최대 3개 반환한다.

- 별도 입력 쿼리를 받지 않는다.
- 응답 항목은 `PublicCourseListItem`을 사용한다.
- 사용자별 좋아요 여부처럼 캐시를 방해하는 개인 데이터는 포함하지 않는다.
- 정적 경로이므로 `/:courseId`보다 먼저 라우터에 등록한다.

기존 코스 상세, 생성, 수정, 삭제 API의 경로와 의미는 바꾸지 않는다.

## 데이터와 조회 구조

### 좋아요 수

많은 공개 코스를 인기순으로 정렬할 때 매 요청마다 모든 좋아요를 집계하지 않도록 코스 문서에 정렬용 `likeCount`를 유지한다.

- 기존 `CourseLike` 문서를 좋아요의 원본 데이터로 유지한다.
- 좋아요 추가와 해제 성공 뒤 코스의 `likeCount`를 일치시킨다.
- 기존 코스는 마이그레이션 또는 일회성 백필로 현재 좋아요 수를 채운다.
- 목록과 상세는 같은 `likeCount` 값을 사용한다.
- 백필 전 누락 값은 0으로 취급한다.

정확한 동시성 처리와 백필 절차는 구현 계획에서 기존 좋아요 서비스 흐름을 기준으로 검증한다.

### 조회

- 코스 목록을 먼저 제한된 개수로 조회한다.
- 포함 상점, 작성자와 필요한 태그·이미지를 ID 묶음으로 조회한다.
- 항목마다 상점과 사용자를 따로 조회하지 않는다.
- 최근 7일 좋아요 후보 조회를 위해 `CourseLike.createdAt` 기반 집계를 지원하는 인덱스를 검토한다.
- 최신순과 인기순, 지역 필터의 실제 쿼리 형태에 맞춰 코스 인덱스를 추가한다.
- `explain` 결과로 인덱스 사용 여부를 구현 단계에서 확인한다.

## 프론트엔드 흐름

### 홈

- 기존 `MOCK_COURSES`를 홈 추천 쿼리로 교체한다.
- 다음 한국 시간 자정까지 데이터를 fresh로 유지한다.
- `더 보기`를 `/courses` 링크로 바꾼다.
- 추천 영역은 홈의 다른 영역과 분리된 로딩, 빈 상태와 오류 상태를 갖는다.
- 영역 오류가 홈 전체를 중단시키지 않게 기존 프론트엔드 오류 격리 규칙을 따른다.

### `/courses`

- 상단에 화면 제목을 표시한다.
- 지역 필터는 가로 스크롤 가능한 칩으로 제공한다.
- 최신순과 인기순을 선택할 수 있는 정렬 컨트롤을 제공한다.
- 선택값은 URL `searchParams`와 동기화한다.
- 공개 코스 카드를 세로 목록으로 표시한다.
- 하단 관찰 지점에 도달하면 다음 커서 페이지를 조회한다.
- 최초 로딩, 다음 페이지 로딩, 빈 결과와 오류를 각각 표시한다.
- 지역 필터 결과가 비었을 때 전체 목록으로 돌아가는 행동을 제공한다.

## 실패와 경계 상황

- 후보가 없으면 홈은 빈 상태를 표시하고 목록 페이지는 공개 코스가 없다는 안내를 표시한다.
- 홈 후보의 지역이 세 곳보다 적으면 같은 지역을 허용해 최대 3개를 채운다.
- 상점이 삭제되었거나 이미지·태그가 없어도 코스 항목 자체는 표시한다.
- 작성자를 찾을 수 없어도 코스 목록 조회를 실패시키지 않는다.
- 공개 목록을 조회한 뒤 사용자 코스가 비공개로 바뀌면 상세 진입 시 기존 권한 정책으로 차단한다.
- 인기순을 보는 동안 좋아요 수가 바뀌어 페이지 경계가 움직일 수 있다. 복합 커서로 흔들림을 줄이되 실시간 스냅샷 고정은 범위에 포함하지 않는다.
- 잘못된 URL 필터는 지원하는 기본값으로 복구하고 API에는 검증된 값만 보낸다.

## 테스트 기준

### 백엔드와 공용 계약

- 공개 추천 코스와 공개 사용자 코스만 목록에 포함한다.
- 비공개 사용자 코스를 제외한다.
- 지역 필터가 정확히 적용된다.
- 최신순과 인기순의 동률 정렬이 안정적이다.
- 각 정렬 커서가 다음 페이지를 중복 없이 반환한다.
- 대표 태그가 빈도와 공용 상수 순서에 따라 최대 2개 선택된다.
- 작성자와 최대 4개 이미지가 목록 항목에 매핑된다.
- 최신 10개와 최근 7일 좋아요 상위 10개가 중복 제거·보충된다.
- 같은 날짜의 홈 결과가 안정적이고 날짜가 바뀌면 다시 선택된다.
- 홈은 다른 지역을 우선하고 부족하면 같은 지역으로 채운다.
- 비공개 전환 시 Pick이 해제된다.
- 누락된 `likeCount`가 0으로 처리되고 백필 결과가 실제 좋아요 수와 일치한다.
- Zod가 잘못된 지역, 정렬, 커서와 limit을 거부한다.

### 프론트엔드

- 홈의 정상, 로딩, 빈 상태와 오류 상태를 검증한다.
- 더 보기가 `/courses`로 이동한다.
- 추천 코스는 `by 소품지도`로 표시한다.
- 사용자 코스는 닉네임을 표시하고 Pick 코스만 뱃지를 표시한다.
- 사진 1~4장과 이미지 실패 상태가 안전하게 표시된다.
- 대표 태그가 최대 2개 표시된다.
- 좋아요 수가 표시된다.
- 지역과 정렬 변경이 URL과 쿼리 키를 바꾸고 첫 페이지부터 조회한다.
- 무한 스크롤이 다음 페이지를 한 번씩 불러온다.
- 320px, 390px와 480px에서 긴 내용과 뱃지가 레이아웃을 깨지 않는다.
- 키보드와 보조 기술로 필터, 정렬과 코스 링크를 사용할 수 있다.

## 구현자가 결정할 수 있는 세부 사항

- 기존 디자인 토큰 안에서 지역·태그·Pick 뱃지의 구체적인 색상과 간격
- 모바일 정렬 컨트롤을 `select`, 메뉴 또는 작은 버튼 그룹 중 어떤 기존 UI로 조합할지
- 결정적인 날짜별 순서를 만드는 해시 함수의 구체적인 구현
- 공개 항목 타입과 쿼리 키의 최종 식별자 이름
- 테스트 fixture의 구체적인 코스 제목, 이미지와 닉네임

이 선택들은 위 정책과 접근성, 기존 컴포넌트 규칙을 바꾸지 않아야 한다.
