# 지도 페이지 상점 마커 노출 트러블슈팅 보고서

## 조사 범위

- 기준 브랜치: `main` (`7f7877c`)
- 조사일: 2026-09-28
- 화면: 모바일 viewport `390 × 844`, `http://localhost:3000/map`
- 코드 수정 없이 정적 분석과 브라우저 런타임 측정만 수행

## 결론

마커 생성 실패가 아니라 **지도 화면과 마커 위치가 서로 다른 지역을 보고 있는 문제**다.

지도는 항상 성수동 좌표 `(37.5445, 127.056)`와 zoom 14로 시작한다. 반면 최초 상점 API는 지도 영역과 무관하게 `latest` 정렬의 첫 10개를 반환한다. 조사 시점의 첫 10개는 모두 홍대·연남 지역이었다.

그 결과 마커 10개는 정상 생성됐지만 모바일 화면 왼쪽 약 1,288~1,429px 밖에 배치됐다. 사용자는 지도에서 마커가 생성되지 않은 것처럼 보게 된다.

## 데이터 흐름

1. `MapScreen`이 `/shops?page=1&limit=10&sort=latest`를 호출한다.
2. 응답 10개를 `toMapShop`으로 변환한다.
3. `NaverMapCanvas`가 성수동 고정 좌표로 지도를 만든다.
4. `NaverMapCanvas`가 응답 좌표로 마커를 정상 생성한다.
5. 지도 중심을 응답 마커에 맞추는 `fitBounds` 또는 최초 상점으로 이동하는 처리가 없다.

## 가설별 검증

### 가설 1. 상점 API가 실패하거나 빈 배열을 반환한다

**결과: 기각**

- 요청: `GET /api/shops?page=1&limit=10&sort=latest`
- 상태: `200`
- 응답: `items` 10개, `totalCount` 43개
- 목록 시트에도 같은 10개가 정상 표시됐다.

### 가설 2. 네이버 지도 Client ID 또는 SDK 로드가 실패한다

**결과: 기각**

- 지도 SDK 요청 상태: `200`
- 지도 인증 요청 상태: `200`
- 지도 타일이 정상 렌더링됐다.
- `missing-key` 또는 SDK 오류 안내도 표시되지 않았다.

### 가설 3. API 좌표가 누락됐거나 위도·경도가 뒤집혔다

**결과: 기각**

- 첫 응답의 위도는 약 `37.5487~37.5653`이었다.
- 첫 응답의 경도는 약 `126.9174~126.9295`였다.
- 주소와 좌표가 모두 홍대·연남 영역으로 일치했다.
- `LatLng(shop.latitude, shop.longitude)` 인자 순서도 올바르다.

### 가설 4. 커스텀 마커 HTML 또는 CSS 때문에 마커가 렌더링되지 않는다

**결과: 기각**

- 클로버 마커 이미지 DOM이 10개 생성됐다.
- 이미지 크기도 정상 계산됐다.
- `/map?shopId=<첫 번째 상점 ID>`로 들어가 기존 `panTo`가 실행되자 같은 마커 10개가 모두 viewport 안에 표시됐다.

즉, 아이콘 자체가 아니라 지도 위치가 문제다.

### 가설 5. 초기 지도 중심과 API 결과 지역이 다르다

**결과: 채택 — 주원인**

| 항목 | 실제 값 |
| --- | --- |
| 초기 지도 중심 | 성수동 `(37.5445, 127.056)` |
| 초기 확대 단계 | `14` |
| 첫 API 결과 | 홍대·연남 10개 |
| 초기 마커 DOM | 10개 |
| 초기 화면 안 마커 | 0개 |
| 초기 마커 x 좌표 | `-1288px` ~ `-1429px` |
| 선택 상점 이동 뒤 화면 안 마커 | 10개 |

지도만 홍대로 이동하자 기존 마커가 모두 보였으므로 원인과 결과가 직접 확인됐다.

### 가설 6. 페이지네이션 때문에 전체 상점 마커가 즉시 생성되지 않는다

**결과: 채택 — 보조 원인**

- 최초에는 43개 중 첫 페이지 10개만 마커로 생성됐다.
- 목록 시트를 펼치고 끝까지 스크롤하자 1~5페이지가 호출됐다.
- 이후 목록 43개와 마커 DOM 43개가 생성됐다.

현재 마커 데이터가 목록 무한 스크롤에 묶여 있다. 사용자가 목록을 스크롤하지 않으면 나머지 33개는 지도에 존재하지 않는다.

## 재현 절차

1. 로그인하지 않은 상태로 `/map`에 접속한다.
2. 상점 목록에 홍대·연남 상점이 보이는지 확인한다.
3. 지도는 성수동을 보여 주지만 마커는 보이지 않는지 확인한다.
4. URL에 첫 상점의 `shopId`를 넣어 다시 접속한다.
5. 지도가 해당 상점으로 이동하면서 마커 10개가 보이는지 확인한다.
6. 목록을 펼쳐 끝까지 스크롤한다.
7. API 2~5페이지가 추가 호출되고 마커 수가 43개로 증가하는지 확인한다.

## 권장 수정 방향

### 1순위: 지도 조회 기준을 먼저 결정

제품 동작을 다음 중 하나로 명확히 정해야 한다.

- **현재 지도 영역 기준 조회**: 지도 중심·반경 또는 bounds를 API에 전달하고, 지도 이동이 끝난 뒤 해당 영역 상점을 조회한다.
- **검색 결과 전체 보기**: 최초 응답 후 모든 마커를 포함하는 bounds를 계산해 `fitBounds`를 실행한다.
- **사용자 위치 중심**: 위치 권한 성공 시 사용자 위치로 이동하고 주변 상점을 조회하며, 실패 시 의도적인 기본 지역을 사용한다.

지도 서비스의 일반적인 기대와 현재 API의 `lat`, `lng`, `radius` 지원을 고려하면 첫 번째 방식이 가장 자연스럽다.

### 2순위: 지도 마커 데이터와 목록 페이지네이션 분리

목록의 10개 단위 무한 스크롤과 지도에 필요한 데이터 범위는 목적이 다르다. 지도는 현재 bounds 안의 상점을 한 번에 받거나 별도 marker 전용 응답을 사용하는 편이 안전하다.

### 3순위: 자동 화면 이동의 발동 조건 정의

검색·필터 변경마다 무조건 `fitBounds`를 실행하면 사용자가 움직인 지도를 빼앗을 수 있다. 다음 시점을 나눠야 한다.

- 첫 진입
- 검색어 또는 태그 필터 변경
- 사용자가 직접 지도 이동
- 상점 선택
- 현재 위치 버튼 선택

## 수정 후 검증 기준

- 첫 진입 시 API가 반환한 마커가 최소 1개 이상 viewport 안에 보인다.
- 상점 응답이 비어 있지 않은데 화면 안 마커가 0개인 상태를 자동 테스트로 잡는다.
- 지도 이동 후 현재 bounds에 맞는 상점만 조회된다.
- 목록을 스크롤하지 않아도 현재 지도 영역의 마커가 모두 생성된다.
- 검색·태그 필터·상점 선택·현재 위치 이동 후 지도 중심 정책이 서로 충돌하지 않는다.
- 320px, 390px, 480px viewport에서 확인한다.

## 조사 중 별도 발견

비로그인 상태에서 각 상점 카드의 픽 폴더 조회가 반복되어 다수의 `401` 요청이 발생한다. 마커 미노출의 직접 원인은 아니지만 네트워크 소음과 불필요한 재시도를 만들 수 있으므로 별도 이슈로 분리하는 편이 좋다.
