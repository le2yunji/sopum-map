## 안정성과 클린 코드

- 컴포넌트와 함수는 한 가지 역할만 맡게 하고, 화면 파일이 데이터 변환·상태 처리·표시를 모두 떠안지 않게 분리한다.
- 외부 데이터는 항상 누락, 빈 배열, 잘못된 값, 느린 응답, 실패 가능성이 있다고 가정한다.
- API 응답을 화면에서 바로 깊게 참조하지 않는다. 경계에서 검증하고 화면에 필요한 안전한 표시 모델로 변환한다.
- 선택 필드에는 의도적인 기본값을 제공한다. 존재하지 않는 이미지, 제목, 태그 때문에 렌더링이 중단되지 않게 한다.
- 목록의 안정적인 식별자를 `key`로 사용한다. 배열 인덱스는 순서가 절대 바뀌지 않는 정적 목록에서만 사용한다.
- 비동기 요청의 중복 실행, 오래된 응답 덮어쓰기, 언마운트 뒤 상태 변경을 막는다.
- 새 함수 바로 위에는 구현 내용을 반복하지 말고 목적이나 중요한 이유를 설명하는 짧은 주석을 작성한다.

## 로딩·빈 상태·오류 상태

- 백엔드 데이터를 사용하는 모든 화면과 독립 섹션은 `loading`, `success`, `empty`, `error` 상태를 명시적으로 처리한다.
- 초기 로딩에는 최종 레이아웃과 크기가 비슷한 스켈레톤을 사용해 화면 흔들림을 줄인다.
- 스켈레톤은 장식 요소로 처리하고 보조 기술에는 간결한 로딩 상태를 전달한다. 무한 애니메이션은 `prefers-reduced-motion`을 존중한다.
- 빈 상태와 오류 상태를 같은 것으로 취급하지 않는다. 빈 상태는 다음 행동을 안내하고 오류 상태는 가능한 경우 다시 시도 동작을 제공한다.
- 이전 데이터가 안전하게 남아 있다면 재검증 중 화면을 비우지 않고 이전 데이터와 갱신 상태를 함께 보여준다.
- 이미지 로딩 실패에는 로컬 기본 이미지를 사용하고 대체 텍스트는 콘텐츠의 의미를 설명한다.

## 오류 격리

- App Router의 주요 라우트에는 필요에 따라 `error.tsx`를 두어 페이지 단위 오류를 격리한다.
- 홈의 큐레이션·추천 코스처럼 서로 독립적으로 데이터를 받는 영역은 섹션 단위 Error Boundary로 감싼다. 한 영역의 렌더링 오류가 전체 앱과 하단 내비게이션을 중단시키면 안 된다.
- Error Boundary의 fallback은 해당 영역의 크기와 맥락을 유지하고 다시 시도 또는 새로고침 동작을 제공한다.
- Error Boundary가 이벤트 핸들러, 비동기 콜백, 서버 오류 응답을 잡아주지는 않는다. 이런 오류는 각 요청과 이벤트 경계에서 명시적으로 처리한다.
- 사용자가 복구할 수 있는 오류는 안내 UI로 처리하고, 개발자가 고쳐야 하는 오류는 숨기지 말고 개발 환경에서 원인을 확인할 수 있게 유지한다.

## UI 방어 처리 완료 기준

- 정상 데이터뿐 아니라 누락 필드, 빈 목록, 긴 텍스트, 깨진 이미지와 느린 응답에서도 레이아웃이 유지된다.
- 연속 클릭과 중복 제출을 막고 처리 중인 컨트롤은 비활성화하거나 진행 상태를 표시한다.
- 실패한 낙관적 업데이트는 이전 상태로 되돌리고 사용자에게 실패를 알린다.
- 오류 안내와 입력 오류는 색상만으로 구분하지 않고 텍스트와 접근 가능한 연결을 제공한다.
- 새 데이터 기반 UI는 정상·로딩·빈 상태·오류 상태를 테스트 또는 Storybook으로 검증한다.

## 사용자 노출 문구

- 화면에서 사용자에게 보여주는 설명, 안내, 빈 상태, 오류 메시지는 존댓말로 작성한다.
- `불러오지 못했어`, `다시 시도해 줘`, `상점이 없음` 같은 반말·음슴체를 사용하지 않는다.
- 짧은 버튼명과 메뉴명은 `다시 시도`, `홈으로 이동`처럼 명확한 행동형 명사구를 사용할 수 있다.
